# Rick IA V2 — Design Specification

## Intent
Rick IA is the personal assistant built into RICK_DEV OS 2.0. It exists to understand Rick's current OS data, relevant personal context, goals and priorities; turn that context into useful analysis; proactively surface relevant reminders; converse naturally by text and voice; and propose safe changes to the OS.

Rick IA is not a generic chatbot. Its personality is close, direct, lightly provocative and humorous without becoming annoying. It must become serious when clarity, money, safety or important decisions require it.

## Core rules
- Rick IA may read and analyze all RICK_DEV OS modules available to the authenticated admin.
- Rick IA may suggest actions proactively.
- Rick IA must never mutate OS data until Rick explicitly confirms the exact pending action.
- Guest mode is read-only and must never expose Rick's private AI profile or conversation history.
- The public GitHub repository must not contain Rick's private personal profile, private conversation history, API secrets or private OS snapshots.
- Personal context is stored server-side/private and is fetched only for the authenticated admin.
- The assistant must distinguish live OS data from stable profile context and must not invent personal facts.

## Personality
- Name: Rick IA.
- Language: Brazilian Portuguese by default.
- Tone: natural, close, direct, confident, lightly sarcastic/provocative when useful.
- Humor is optional and must never reduce clarity or respect.
- No corporate-assistant filler.
- Do not praise every action or automatically agree with Rick.
- Challenge contradictions between a proposed action and Rick's own stated priorities.
- When the situation is serious, remove the teasing tone and be concise and practical.

## Context model
Rick IA receives four layers:
1. **Identity prompt** — what Rick IA is, why it exists, tone and non-negotiable rules.
2. **Private Rick profile** — only stable/relevant personal context that improves assistance. This is private server-side data, not source-controlled.
3. **Live OS snapshot** — current data from RICK_HOME, RICK_STUDY, RICK_FIT, RICK_FINANCE, RICK_LAB and RICK_SYSTEM, normalized and minimized for the current request.
4. **Conversation context** — recent messages and durable assistant preferences/history appropriate to the authenticated admin.

## UI
- A floating Rick IA button is available on every authenticated admin screen.
- Clicking it opens a compact panel without navigating away from the active module.
- The panel supports text chat, message history, pending-action cards, microphone controls and spoken replies.
- The floating button may show an unread/proactive-insight badge.
- Proactive insights may interrupt inside the OS when relevant, but trivial/repetitive interruptions should be throttled.

## Safe actions
Assistant actions are two-phase:
1. Rick IA produces a typed pending action with a human-readable preview of the exact mutation.
2. The UI asks Rick to Confirm or Cancel.
3. Only Confirm invokes the mutation path.
4. The mutation passes through the same validation/normalization rules used by the OS and the existing cloud synchronization model.

Initial action families should cover adding/updating tasks, projects, finance records, study progress, fitness records and other existing validated record types. Destructive actions require an especially explicit preview and confirmation.

## Backend
Use a Supabase Edge Function as the trusted boundary between the React client and the AI provider. API keys remain in Supabase project secrets. The Edge Function validates the authenticated user, loads only authorized private context, receives a minimized live OS snapshot, calls the current OpenAI Responses API, validates structured assistant outputs, and returns either a normal assistant message or a pending-action proposal.

The existing React client continues to own its normalized application state and cloud-sync flow. Rick IA does not bypass those safeguards.

## Voice
V2 begins with push-to-talk: record a bounded voice message, transcribe it, run it through the same Rick IA text-agent path, then optionally play a spoken response. Voice must feel feminine, calm, confident and lightly teasing, without cloning or impersonating a real person's voice. The UI must disclose that the voice is AI-generated.

The implementation should avoid starting a new integration on an API path scheduled for near-term shutdown. Conversational/live voice can later move to the current Realtime/GPT-Live path without changing Rick IA's core prompt or action contracts.

## Proactivity
Proactivity is a separate subsystem on top of the same assistant/context model. It may create insights from OS state such as stalled projects, upcoming goals, unusual spending or neglected routines. The first implementation may compute insights when the app opens or state changes; scheduled background checks are a later phase.

## Privacy and security
- Never commit private profile text or secrets to this public repository.
- Keep the OpenAI API key and privileged Supabase credentials server-side only.
- Use authenticated user identity rather than user-editable metadata for authorization.
- Keep RLS enabled on every exposed private table and restrict rows to the owner.
- Avoid sending fields to the AI provider that are irrelevant to the user's current request.
- Conversation/profile storage must be separable from the main OS state so the user can later clear or revise it independently.

## Delivery phases
1. Core prompt/context contracts + floating text chat.
2. Structured pending actions + explicit confirmation and validated mutation.
3. Private conversation/profile persistence.
4. Proactive in-app insights/interruptions.
5. Push-to-talk transcription + spoken responses.
6. Optional future Realtime/GPT-Live conversational voice.
